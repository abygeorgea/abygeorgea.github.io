# API Automation

The Constitution in `agent.md` applies to everything here (OpenAPI as source of truth, `z.strictObject`, the `expect(Schema.parse(body)).toBeTruthy()` pattern, `test.step` for 2+ calls, no empty-body-only 400s, no silent coverage drops, sources of truth for URLs/paths). This skill holds the how-to and the rules the Constitution does not cover.

Additional rules:

- A `null` body (401, 403, 204) is asserted with `expect(body).toBeNull()`, not parsed.
- No `as T` casts to cross a type boundary; parse with Zod instead.
- Always fuzz path parameters with the invalid-format loop, whether or not OpenAPI mentions it.
- Use `apiRequest` directly; promote to a helper fixture only when the same setup/teardown is reused across 3+ spec files.
- Never use `process.env.API_URL` bare; combine it with an enum path. Token env vars: `ACCESS_TOKEN` (full permissions) and `ACCESS_TOKEN_ZERO` (zero permissions), populated by the auth bootstrap helper.

## 1. Source the contract

1. **Documentation exists (normal case):** build schemas and tests strictly from it: field names, types, required/optional, nullability, status codes, error shapes. Do not curl first and match the schema to reality.
2. **No documentation:** make a real request to discover structure, types, optional fields, nested shapes and error formats; treat the findings as the working contract and flag the missing docs to the team. This is a stopgap, not a target state.

## 2. Zod schemas

Location: `fixtures/api/schemas/{area}/` (app schemas) and `fixtures/api/schemas/util/` (shared error schemas). Resolve `{area}` with `ls fixtures/api/schemas/`.

Spell out the response envelope per endpoint exactly as the spec describes it; do not invent a factory helper. If an envelope genuinely repeats across many endpoints in one domain, extract a per-domain `_envelope.ts` `z.strictObject` and compose with `.extend(...)`, only after the repetition is real.

```typescript
import { z } from 'zod/v4';
import type { output as zOutput } from 'zod/v4';

export const ProductSchema = z.strictObject({
    id: z.uuid(),
    name: z.string().min(1),
    price: z.number().positive(),
    category: z.enum(['electronics', 'clothing', 'food']),
    inStock: z.boolean(),
});

export const CreateProductResponseSchema = z.strictObject({
    success: z.boolean(),
    message: z.string(),
    data: ProductSchema,
    errors: z.unknown().nullable(),
});

export type CreateProductResponse = zOutput<typeof CreateProductResponseSchema>;
```

**Existing error schemas** (`util/errorResponseSchema.ts`): `BadRequestResponseSchema` (400), `UnauthorizedResponseSchema` (401), `ForbiddenResponseSchema` (403), `NotFoundResponseSchema` (404).

**Inference:** `zOutput<typeof S>` is the post-parse type (response types, 99% of cases); `zInput<typeof S>` is the pre-parse type (request payloads where defaulted fields may be omitted). Without `.default()`/`.transform()` they are identical; prefer `zOutput`.

### Zod 4 validators

| Data | Validator | Data | Validator |
|---|---|---|---|
| UUID | `z.uuid()` | Enum | `z.enum([...])` / `z.enum(MyEnum)` |
| GUID | `z.guid()` | Literal | `z.literal(200)` |
| Email | `z.email()` | Optional | `.optional()` |
| URL | `z.url()` | Array | `z.array(S)` |
| Non-empty | `z.string().min(1)` | Union | `z.union([...])` |
| Integer | `z.int()` | ISO date / datetime | `z.iso.date()` / `z.iso.datetime()` |
| IPv4 | `z.ipv4()` | Base64 | `z.base64()` |

Deprecated forms to avoid: `z.string().email()/uuid()/url()` (use the top-level validators), `z.nativeEnum(E)` (use `z.enum(E)`), `.merge()` (removed; use `.extend()` or spread `.shape`), `.passthrough()` (use `z.looseObject()` only when explicitly needed), `z.infer` (use `zOutput`/`zInput`).

## 3. Write the test with `apiRequest`

```typescript
import { expect, test } from '../../../fixtures/pom/test-options';
import { UserResponse, UserResponseSchema } from '../../../fixtures/api/schemas/app/userSchema';
import { ApiEndpoints } from '../../../enums/app/app';

test('should return user data', { tag: '@api' }, async ({ apiRequest }) => {
    const { status, body } = await apiRequest<UserResponse>({
        method: 'GET',
        url: ApiEndpoints.CURRENT_USER,
        baseUrl: process.env.API_URL,
        headers: process.env.ACCESS_TOKEN,
    });

    expect(status).toBe(200);
    expect(UserResponseSchema.parse(body)).toBeTruthy();
});
```

The generic `<UserResponse>` gives compile-time safety on `body`; `parse` gives runtime validation. Use both.

| Option | Type | Req. | Notes |
|---|---|---|---|
| `method` | `'GET' \| 'POST' \| 'PUT' \| 'DELETE' \| 'PATCH'` | yes | |
| `url` | `string` | yes | endpoint path (enum) |
| `baseUrl` | `string` | no | prepended |
| `body` | `Record<string, unknown>` | no | payload |
| `headers` | `string` | no | auth token for the Authorization header |
| `authType` | `'Bearer' \| 'Token' \| 'Basic'` | no | default `'Bearer'` |

Use `apiRequest` directly for assertions, `beforeEach`/`afterEach` setup and teardown, and one-off calls.

## 4. `test.step` for multi-call tests

Each call gets its own descriptive step with its own validation:

```typescript
await test.step('Create user via POST /api/users', async () => {
    const { status, body } = await apiRequest<UserResponse>({ method: 'POST', url: ApiEndpoints.USERS, baseUrl: process.env.API_URL, headers: process.env.ACCESS_TOKEN, body: userData });
    expect(status).toBe(201);
    expect(UserResponseSchema.parse(body)).toBeTruthy();
    userId = body.id;
});
await test.step('Delete user via DELETE /api/users/:id', async () => {
    const { status, body } = await apiRequest<null>({ method: 'DELETE', url: `${ApiEndpoints.USERS}/${userId}`, baseUrl: process.env.API_URL, headers: process.env.ACCESS_TOKEN });
    expect(status).toBe(204);
    expect(body).toBeNull();
});
```

Without steps the trace is one blob and reporting cannot show which call failed. A single-call test may skip the step.

## 5. Status-code matrix

For every endpoint x method, cover **every status code in the OpenAPI spec** plus these baselines:

| Scenario | Status | Assert |
|---|---|---|
| Happy path (valid auth + body) | 200/201 | schema parse + key fields match sent data |
| Missing Authorization | 401 | status; error schema or `toBeNull()` |
| Wrong-role token | 403 | status; error schema or `toBeNull()` |
| Empty body (POST/PUT/PATCH) | 400/422 | one test with `{}`, error schema |
| Each required field omitted | 400/422 | one test per field (section 7) |
| Each field, invalid type | 400/422 | `for...of` per field (section 7) |
| Non-existent resource id | 404 | status (`test.skip` + FIXME on backend bug) |
| Invalid path parameter formats | 404 | data-driven loop |
| Unsupported HTTP method | 405 | at least one |
| Conflict (if in spec) | 409 | test it, or `test.skip` + FIXME if not reproducible |
| Validation errors (if in spec) | 422 | covered by per-field tests |
| DELETE no content | 204 | status + `toBeNull()` |

**Structure:** one `test.describe` per HTTP method + path. Use `beforeAll`/`afterAll` (not `beforeEach`/`afterEach`) for resources shared by several tests in the describe. POST describes clean up in `afterAll` the `resourceId` captured in the happy-path test; GET/PUT/DELETE describes create in `beforeAll`. Tag `@api` (check existing specs for other areas).

## 6. Behaviour mismatches

When actual behaviour differs from the spec or the matrix:

1. Write the test as the spec says (expected status and schema).
2. Wrap it in `test.skip` with a `// FIXME:` explaining the discrepancy:

```typescript
/* eslint-disable playwright/no-skipped-test */
// FIXME: <ticket-url> API returns 500 instead of 422 for invalid price on PUT. Backend bug.
test.skip('should return 422 when price is a non-numeric string', { tag: '@api' }, async ({ apiRequest }) => {
    // body as it SHOULD work per spec
});
```

3. Never adjust the expected status to match buggy behaviour, and never loosen the schema to accept drift.
4. If the API returns a different **valid** code than the spec (422 vs 400), use the actual code and comment the spec discrepancy.

## 7. Negative and validation coverage

Endpoints with a body need: (1) an empty-body test, (2) each required field omitted, (3) each field with type-inappropriate values, (4) boundary values where applicable (empty string for min-length, negative for positive-only, past dates for future-only).

- **Per-field invalid types:** base valid payload, override one field at a time with `INVALID_*` values, assert `400` + `BadRequestResponseSchema.parse(body)`.
- **Omitting required fields:** `const { [field]: _, ...rest } = validPayload;` per required field.
- **Path parameters:** data-driven loop over `[{ description, value }]` (numeric strings, boolean-likes, special characters, injection attempts).

Where the invalid-value arrays live is defined in `framework` (test data, three tiers). Universal `INVALID_*` arrays are imported from `test-data/static/util/invalid-values.ts` and never redefined. For an email field, combine the type-mismatch array with the domain invalid-format set.

## 8. Helper fixtures (when needed)

For critical recurring setup/teardown reused across multiple test files, add a helper fixture in `fixtures/helper/helper-fixture.ts`: setup before `await use(data)`, teardown after, which runs even if the test fails.

| Approach | Use for |
|---|---|
| `apiRequest` fixture (default) | all calls: assertions, hooks, one-offs |
| Helper fixture | critical setup reused across 3+ files with guaranteed lifecycle (e.g. a user account 10+ files depend on) |
| Factory | generating dynamic data, no API call |

- **`ZodError` from `parse`:** with a documented contract it is a bug (section 6); without docs, update the schema to the real shape.
- **401 with a null body failing a schema parse:** assert `toBeNull()` instead.
- **`process.env.ACCESS_TOKEN` undefined:** the auth bootstrap did not run (see helpers in `framework`).
- **Other failures:** see the debugging section of `framework`.

# framework-creation

The Constitution in `agent.md` applies to everything here (imports, DI, tags, state cleanup, no magic numbers, no hardcoded content, no JSON static data, Faker for happy-path data, lint gate). This skill holds the detail behind it plus the rules the Constitution does not cover.

Additional rules:

- Every config property needs JSDoc naming its env var; every new env var goes in `env/.env.example` with a safe placeholder. Only `env/.env.example` is tracked.
- Static data files export literal `as const` values only: no runtime imports (type-only is fine), no functions, no Faker, no computed values.
- App-defined strings (messages, labels, paths) are never generated with Faker; they live in enums.
- Edits to existing enum values or static data go through section 9.
- Never suppress a failure: no `test.skip` without `// FIXME: <ticket-url>`, no loosened assertions, no timeout bumps, no `try/catch` around `expect`.

## 1. Spec structure and tags

Locations (resolve `{area}` with `ls tests/`):

| Type | Directory | Covers |
|---|---|---|
| Functional | `tests/{area}/functional/` | one behaviour in isolation |
| API | `tests/{area}/api/` | contracts and schemas (rules in `api-automation`) |
| E2E | `tests/{area}/e2e/` | one multi-feature user journey per test |
| Setup | `tests/{area}/` | `*.setup.ts` auth or preconditions |

```typescript
import { expect, test } from '../../../fixtures/pom/test-options';

test.describe('Feature Name', () => {
    test.beforeEach(async ({ appPage }) => {
        await appPage.openHomePage();
    });

    test('should do expected behavior', { tag: '@smoke' }, async ({ appPage }) => {
        await test.step('GIVEN ...', async () => { /* ... */ });
        await test.step('WHEN ...', async () => { /* ... */ });
        await test.step('THEN ...', async () => { /* ... */ });
    });
});
```

- Web-first assertions only (`toBeVisible`, `toHaveText`, `toBeEnabled`, `toHaveCount`). Awaiting a response belongs in a page-object action, not the spec.
- Tests are independent: no ordering, no shared mutable state. Use `beforeEach` and fixtures for shared setup, and the `resetStorageState` fixture for login/logout flows.
- Data-driven tests loop outside `test()` over named `as const` exports:

```typescript
for (const { description, email, password } of INVALID_LOGIN_ATTEMPTS) {
    test(`should show error for ${description}`, { tag: '@regression' }, async ({ appPage }) => { /* ... */ });
}
```

### Tags

One per test, set with `{ tag: '@x' }` on the test (the rules are in the Constitution).

| Tag | Use |
|---|---|
| `@smoke` | critical path, run first and often |
| `@sanity` | key functionality |
| `@regression` | full coverage of one behaviour |
| `@e2e` | multi-feature journeys |
| `@api` | API contract and schema tests |
| `@destructive` | mutates shared/global state (locale, permissions, roles, guest access, feature flags, global settings, shared seed data such as "delete all users") |

A test that creates its own record and deletes only that record is isolated, not destructive: keep its importance tag, but it still needs the cleanup hook:

```typescript
test.afterEach(async ({ apiRequest }) => {
    await apiRequest({ method: 'POST', url: ApiEndpoints.RESET_DATA, baseUrl: process.env.API_URL, headers: process.env.ACCESS_TOKEN });
});
```

`ApiEndpoints.RESET_DATA` is illustrative; use your app's reset endpoint from `enums/`. `@destructive` tests are excluded from `npm test` (`--grep-invert @destructive`) and run only with `npm run test:destructive` (`--workers=1`); since each test has one tag, they never run under `test:smoke`, `test:regression`, etc.

## 2. Type safety

- At a boundary (network, file, input) use `unknown` and convert via `Schema.parse(...)`. Inside a function body every variable has a concrete type.
- `"strict": true` stays on, per file as well. Parameter types are explicit; exported and public functions have explicit return types (`Promise<void>`, `Locator`, `string`, ...).
- `process.env.X` is `string | undefined`. Resolve it at the access point: `process.env.APP_URL!` when guaranteed at runtime, or `process.env.ENVIRONMENT ?? 'dev'` with a safe default. Never export an unresolved value (`export const baseUrl = process.env.API_URL;`).
- Zod schema rules and validators are in `api-automation`.

## 3. Test data

| Value kind | Home |
|---|---|
| Happy-path dynamic data (emails, names, ids, text) | Faker factory in `test-data/factories/{area}/*.factory.ts` |
| Universal type-mismatch values | import from `test-data/static/util/invalid-values.ts` |
| Domain-specific curated invalid sets (bad emails, weak passwords, forbidden categories, locales) | `.ts` with `as const` in `test-data/static/{area}/` |
| Field-specific boundary values used in one place | inline in the spec; promote to static only when reused by 2+ fields or specs |
| App-defined strings | `enums/{area}/*` (section 4) |
| Single-assertion expected values | inline in the test |
| Timeouts, retries, workers | `playwright.config.ts` (section 5) |

If a value fits no row, ask; do not invent a location. Resolve `{area}` with `ls test-data/static/` and `ls test-data/factories/`.

**Factory pattern:** Faker + Zod, accept `overrides`, validate with the schema, return the Zod-inferred type, JSDoc with `@param`/`@returns`:

```typescript
export const generateUser = (overrides?: Partial<UserResponse>): UserResponse => {
    const defaults: UserResponse = { id: faker.string.uuid(), email: faker.internet.email(), token: faker.string.alphanumeric(64) };
    return UserResponseSchema.parse({ ...defaults, ...overrides });
};
```

**Static shapes:** Shape A, per-field arrays (`INVALID_EMAILS = [...] as const`); Shape B, scenario rows with a `description` (`INVALID_LOGIN_ATTEMPTS = [{ description, email, password }] as const`). Use A for one-field-at-a-time loops, B when fields must be tested together.

**Universal arrays already exist** (import, never redefine): `INVALID_STRING_VALUES` `[123, true, null, undefined]`, `INVALID_NUMBER_VALUES` `['string','123',true,null,undefined]`, `INVALID_BOOLEAN_VALUES` `['yes',1,0,null,undefined]`, `INVALID_UUID_VALUES` `['not-a-uuid','',123,null,undefined]`, `INVALID_ENUM_VALUES` `['invalidValue','',123,null,undefined]`, `INVALID_ARRAY_VALUES` `['string',123,null,undefined,{}]`, `INVALID_OBJECT_VALUES` `['string',123,null,undefined,[]]`. API consumption patterns are in `api-automation` section 7.

**Magic numbers:** prefer web-first assertions. If a number is unavoidable: suite tuning goes to `playwright.config.ts`, domain limits to an enum, and a single legitimate per-assertion override is passed inline (`{ timeout: 10000 }`) with a one-line justification.

## 4. Enums

- TypeScript `enum` (not `as const` objects). Name PascalCase (`Messages`, `ApiEndpoints`, `Roles`, `StorageStatePaths`), members SCREAMING_SNAKE_CASE, value exactly as the app uses it. JSDoc on every enum.
- Locations: `enums/{area}/*.ts` for app-defined values, `enums/util/*.ts` for shared ones (e.g. `Roles`). Resolve `{area}` with `ls enums/`. Extend an existing enum file before creating a new one.
- In an enum: endpoint paths, routes, storage-state paths, app-defined UI messages, roles, status codes. Not in an enum: URLs, credentials and tokens (config, section 5), curated test inputs (section 3), tuning numbers, and strings used in exactly one place (inline). An array is not an enum.
- **UI message values must be captured from the live app** via `playwright-cli` (see `ui-automation`), never guessed. If the app is unavailable, add `// FIXME: unverified` and flag it; do not ship unverified messages.

## 5. Config and environment

| Value | Home |
|---|---|
| App under test URLs | env var + `config/app.ts` (`appConfig.appUrl`, `apiUrl`) |
| Utility / third-party service URL | env var + `config/util/util.ts` (`utilityConfig.*`) |
| Credentials (email, password, keys) | env var only; no config object |
| Endpoint paths, routes, storage-state paths | enums (section 4) |
| Timeouts, retries, workers | `playwright.config.ts` |
| `ENVIRONMENT`, `CI` | shell level only; not in `.env.example` |

`playwright.config.ts` loads `./env/.env.${ENVIRONMENT ?? 'dev'}` with dotenv. A missing file silently loads nothing and every `process.env.*` is `undefined`. Override per run: `$env:ENVIRONMENT = 'staging'; npx playwright test`.

Adding a variable: (1) add it to `env/.env.example` with a safe placeholder, grouped under a comment; (2) add the real value to your untracked `env/.env.<environment>`; (3) only if it is a URL or infra setting worth documenting, add a config property with JSDoc:

```typescript
export const utilityConfig = {
    /** Reporting service base URL loaded from REPORTING_URL env variable */
    reportingUrl: process.env.REPORTING_URL,
};
```

Consume by direct `process.env.*` (dominant in tests, fixtures, helpers) or by config object; do not mix them in one file without reason. `ACCESS_TOKEN` and `ACCESS_TOKEN_ZERO` are populated by the auth bootstrap helper and are not in `.env.example`. If `env/.env.dev` was committed: `git rm --cached`, confirm `.gitignore`, rotate exposed credentials.

## 6. Helpers vs fixtures

| Need | Home |
|---|---|
| Pure function, no lifecycle | helper: `helpers/{area}/` (app-specific: auth bootstrap, storage state, seeding) or `helpers/util/` (generic) |
| Needs DI (`page`, `request`) or setup, `use(data)`, teardown | fixture under `fixtures/` (API lifecycle: `api-automation` section 8) |
| Locators and interactions on a page | page object (`ui-automation`) |
| One-off API call in one test | `apiRequest` directly |
| Dynamic data generation | factory (section 3) |

Helper rules: plain functions (no `use()`, no `base.extend`); camelCase verbs; explicit return types; JSDoc with `@param`/`@returns`; env and enums as in section 5. API calls inside a helper validate with the same `expect(Schema.parse(body)).toBeTruthy()` pattern. Mutating `process.env` is allowed only in auth-bootstrap helpers that publish a token; elsewhere return values through the signature. Prefer extending an existing helper file. Auth bootstrap runs from `tests/{area}/auth.setup.ts` before the main suite.

Fixture rules: new page objects are registered in `fixtures/pom/page-object-fixture.ts` (see `ui-automation`); fixtures are merged in `fixtures/pom/test-options.ts`; a fixture may call helpers but owns the lifecycle.

## 7. Debugging

Read the failure message first: Playwright names the test, the locator or assertion, received vs expected, and the source line. Reproduce narrowly before opening any tool:

```
npx playwright test <file> --workers=1 --retries=0
npx playwright test --grep "<title>" --workers=1 --retries=0
```

`test.only` is fine locally for narrowing, never committed (`forbidOnly` fails CI). Never push a fix you cannot reproduce locally.

### Capture defaults (`playwright.config.ts`)

Trace `on-first-retry` (locally `retries: 0`, so no trace unless you pass `--trace on` or use UI Mode); screenshot `only-on-failure`; video `retain-on-failure`; HTML report opens on failure locally; blob report on CI. Timeouts: action 10 s, navigation 30 s, `expect` 10 s, test 60 s. Knowing which one fired tells you whether it is an action, navigation, assertion or pacing problem.

### Classify, then pick the tool

| Failure | Likely cause | Look at |
|---|---|---|
| Action timeout | wrong locator, disabled element, page not loaded | trace action panel + DOM snapshot |
| Assertion timeout | element genuinely not visible, wrong locator, navigation race | UI Mode, snapshot before the assertion |
| Navigation timeout | wrong URL, env not set, app down | `process.env.APP_URL`, `env/.env.${ENVIRONMENT}` |
| Strict-mode violation | locator too loose | `ui-automation` locator guidance |
| `expect()` mismatch | page state, data or enum drifted | received vs expected; enum drift goes to section 9 |
| `ZodError` | response disagrees with schema | `api-automation` sections 2 and 6 |
| Network error (`ECONNREFUSED`, ENOTFOUND, 5xx) | wrong base URL, app down, missing env or token | env vars, auth bootstrap |
| Element not attached | action raced navigation or frame swap | trace; add `waitForResponse` or a web-first assertion in the page action |
| `ReferenceError` / undefined fixture | fixture not registered, or a spec imports from `@playwright/test` | section 6, Constitution imports rule |
| Passes alone, fails in suite | independence violated, shared state, parallel collision | section 1; promote shared mutators to `@destructive` with cleanup |
| `forbidOnly` build failure | committed `test.only` | remove it |

| Command | Use |
|---|---|
| `npm run test:ui` | UI Mode, the first choice (timeline, locator picker, watch mode, network tab) |
| `npm run test:debug` | Inspector, step with F10 |
| `npm run test:headed` | watch the browser (excludes `@destructive`) |
| `npm run report` | open the last HTML report |
| `npx playwright show-trace <trace.zip>` | GUI Trace Viewer |
| `npx playwright trace open <trace.zip>` then `actions`, `action <id>`, `snapshot <id> --name before\|after`, `requests`, `console`, `errors`, `screenshot <id>`, finally `trace close` | CLI trace inspection (Playwright 1.59+), for headless or agent use |
| `npx playwright test --debug=cli` | CLI debugger: prints `playwright-cli attach <id>`; drive with `step-over`, `snapshot` |
| `npx playwright test <file> --trace on --workers=1 --retries=0 --headed` | force-everything-on local investigation |

Pick one tool; do not bounce between three.

### Fix at the root cause

| Diagnosis | Fix lives in |
|---|---|
| Locator wrong, zero or many matches | the page object getter |
| Action raced ahead of navigation | the page object action method |
| `Messages.X` drifted from the live UI | `enums/` via section 9 |
| Schema disagrees with documented contract | the test: `test.skip` + FIXME (`api-automation` section 6); never loosen the schema |
| Schema disagrees with real response, no docs | the schema |
| Token undefined | auth bootstrap helper or `auth.setup.ts` |
| Fixture undefined | `fixtures/pom/page-object-fixture.ts` |
| Hardcoded string in `getByText` | replace with an enum |
| Test depends on another test | move setup to `beforeEach` or a fixture; use a factory for unique data |

After the fix: re-run the affected file with `--workers=1 --retries=0` (five consecutive green runs for a flake fix; in PowerShell `for ($i=1; $i -le 5; $i++) { npx playwright test <file> --workers=1 --retries=0; if ($LASTEXITCODE) { break } }`), then `npm test` and `npm run check`, and confirm no `test.only` remains.

### CI-only failure

1. Download artifacts (`gh run download <run-id> -n playwright-report`), unzip, find trace zips under `data/`.
2. Open them with `show-trace` or the CLI trace commands above.
3. Compare environments: env file, whether `auth.setup.ts` produced `.auth/app/appStorageState.json`, viewport (`1920x1080` in the chromium project), browser version.
4. Replay: `$env:ENVIRONMENT='ci'; $env:CI='1'; npx playwright test <file> --workers=1 --retries=0`.
5. Still green locally: add temporary instrumentation or `--trace on`, run in CI, inspect, then **remove the instrumentation** before merging.

## 9. Refactoring enum values and static data

Use before changing an enum value, renaming an enum key, or editing any existing `test-data/static/**` file. To add new ones, use sections 3 and 4.

1. **Find all consumers first.** Search the whole repo for the enum key **and** the raw string value (hardcoded copies bypass the enum): `rg "Messages.LOGIN_ERROR" .` and `rg "Invalid email or password" .`; for endpoints also `rg "'/api/users/login'" .`. Expect hits in `.ts`, `.md` (skill files, README) and ignorable `.json` reports. Inspect each match; never one global find-and-replace.
2. **Categorise impact.**

| Change | Consumers to check |
|---|---|
| Enum value | hardcoded old strings in `toHaveText`/`toBeVisible`; `z.literal`/`z.enum` in schemas (update to the new value, never loosen to `z.string()`); endpoint paths in `apiRequest`; static data using the old value; derived enum members |
| Enum key rename | every importer (tsc catches), barrel/re-export files, `.md` docs |
| Static data value | tests looping over the export; tests asserting a specific value; enum members mirroring the string |

3. **Change atomically:** source and all consumers in one commit, no intermediate broken state.
4. **Verify:** `npx tsc --noEmit`, `npx eslint .`, then the affected tests (`--grep` matches tags and titles; for one spec run the file).

# UI Automation

## 1. Explore the live app (before any locator is written)

1. **Open and authenticate:** `playwright-cli open <APP_URL>`, then `playwright-cli snapshot`. If the page fails to load or needs auth: stop, tell the human exactly what happened and what you need ("The application at `<URL>` returned [error / login page / blank screen]. I need [credentials / a different URL / auth setup] before I can proceed."), wait, then re-verify.
2. **Explore like a user:** walk the feature, snapshot at each state (`playwright-cli snapshot`, `playwright-cli click <ref>`, `playwright-cli snapshot`), trigger CRUD to capture the real validation and success text, and record each element's role, accessible name, label and test id. Look for forms, buttons, navigation, feedback elements and dynamic content (modals, expanded sections, new rows).
3. **Plan coverage** (no approval needed): happy paths, validation paths, error paths, edge cases (boundary input, concurrent operations, empty states). Cross-check user stories or acceptance criteria if they exist. The plan decides which feedback locators the page object needs.
4. Encode captured message text as enum values (see `framework`, enums).

## 2. Choose locators

Move down only when the previous option is not feasible.

```typescript
page.getByRole('button', { name: 'Submit' });   // 1 buttons, links, headings, textboxes, checkboxes, navigation
page.getByLabel('Email');                        // 2 labelled inputs (prefer over role textbox)
page.getByPlaceholder('Search...');              // 3 inputs without labels
page.getByText(Messages.LOGIN_ERROR);            // 4 static content; repeated strings come from enums
page.getByTestId('user-avatar');                 // 5 last resort
```

- If an element has a role, prefer `getByRole`.
- If exact text could match several elements, add `{ exact: true }` or use a more specific role.
- Scope inside a container: `page.getByRole('form').getByRole('button', { name: 'Save' })`.
- CSS (`.btn-primary`, `#submit`) only as an absolute last resort via `page.locator()`.

### Feedback locators (every form or CRUD page)

| Feedback | Strategy |
|---|---|
| Success / error message | `getByText(Messages.X)` or `getByRole('alert')` |
| Field validation | `getByText(...)` scoped to the form or field container |
| Toast | `getByRole('status')` or `getByText()` on its content |
| Loading | `getByRole('progressbar')` or `getByText('Loading...')` |
| Empty state | `getByText('No items found')` or the heading in the empty state |

`Messages.*` names here are illustrative; use the real enum members, with text captured via `playwright-cli`.

## 3. Page objects

Location: `pages/{area}/[name].page.ts`; components in `pages/components/[name].component.ts`. Resolve `{area}` with `ls pages/`.

```typescript
import { expect, Locator, Page } from '@playwright/test';
import { Messages } from '../../enums/app/app';

export class ExamplePage {
    constructor(private readonly page: Page) {}

    // ==================== Locators ====================
    get emailInput(): Locator {
        return this.page.getByLabel('Email');
    }
    get submitButton(): Locator {
        return this.page.getByRole('button', { name: 'Submit' });
    }

    // ==================== Feedback Locators ====================
    get successMessage(): Locator {
        return this.page.getByText(Messages.LOGIN_SUCCESS);
    }
    get errorMessage(): Locator {
        return this.page.getByText(Messages.LOGIN_ERROR);
    }

    // ==================== Actions ====================
    /**
     * Submits the form and waits for the API response.
     * @param {string} email - The user's email address.
     * @returns {Promise<void>}
     */
    async submitForm(email: string): Promise<void> {
        await this.emailInput.fill(email);
        await this.submitButton.click();
        await this.page.waitForResponse((r) => r.url().includes('/api/submit'));
    }
}
```

- Locators are `get` accessors returning `Locator` (a style convention; `Locator` is lazy, so a `readonly` field behaves the same). Constructor is always `private readonly page: Page`.
- Page objects import `expect, Locator, Page` from `@playwright/test`, not from `test-options.ts` (that is for specs and fixtures).
- Three sections: interactive locators, feedback locators, action methods.
- Action methods are complete user actions with an explicit return type and JSDoc (`@param`, `@returns`; `@example` encouraged for non-trivial ones). They wait for API responses or state changes (`waitForResponse`, web-first assertions). Plain actions do not assert; a verification method (`xxxAndVerify()`) combines an action with a reusable success check and may use `expect`, and it also needs JSDoc. JSDoc is allowed on component fields.

### Components

Reusable fragments (header, modal, sidebar) become components composed into pages:

```typescript
export class DashboardPage {
    /** Navigation component for header/nav interactions */
    readonly nav: NavigationComponent;
    constructor(private readonly page: Page) {
        this.nav = new NavigationComponent(page);
    }
}
// in a test: await dashboardPage.nav.logout();
```

### Register the fixture

In `fixtures/pom/page-object-fixture.ts`: import the class, add the property to `FrameworkFixtures`, add the body (`dashboardPage: async ({ page }, use) => { await use(new DashboardPage(page)); }`). `pageObjectFixture` is already merged into `test-options.ts`, so no `mergeTests()` change is needed. Specs then take `async ({ dashboardPage }) => ...`.

Before writing a page object, resolve `{area}`, extend any enum it needs (`framework`) and confirm API schemas exist for any call it waits on (`api-automation`).

## 4. The `ui` driver and tools

Use the `ui` fixture (`helpers/ui/ui-driver.ts`) for generic reusable actions and for applications with iframes or heavy AJAX. Ordinary screens still get page objects.

Describe elements with a **target**, never a raw selector: `{ role, name } | { label } | { placeholder } | { text } | { testId } | { css }` plus optional `exact`, `nth`, in the same priority as section 2. `css` rejects volatile ids (`#field-9823471`, hashes, long counters).

| Member | Purpose |
|---|---|
| `ui.goto(url)` | Navigate, wait for idle |
| `ui.click(target)` | Idle, resolve scope, click, idle (retries on frame churn) |
| `ui.fill(target, value, { commit? })` | Fill, then Tab so on-change logic runs |
| `ui.select(target, option)` | Native select or ARIA combobox |
| `ui.readTable(target)` | Table/grid to header-keyed rows |
| `ui.textOf(target)` | Trimmed inner text |
| `ui.locate(target)` / `ui.scope()` | Locator / current scope, for web-first assertions |
| `ui.waitForIdle()` | Settle (pending requests and busy indicators if tracking is configured, else the `load` state) |

- Never store a `Locator`/`FrameLocator` across actions; frames can be recreated. Call `ui.locate(target)` when you need one.
- Custom driver: `new UiDriver(page, { frames: { selectors: ['iframe[name^="work"]'], maxDepth: 2 }, load: { busySelectors: ['.spinner'] } })`, then `dispose()` at the end. Subclass it for a pack (see `pega/PegaPage.ts`).
- **Tools:** `tools.run(name, input)` validates `input` with the tool's Zod schema and runs it. Catalog: `tools/CATALOG.md` (`npm run tools:catalog`). Add a tool with `defineTool` in `tools/ui-tools.ts` or `tools/api-tool.ts`, register it in `tools/index.ts`, regenerate the catalog, and add a case to `tests/framework/ui-driver.spec.ts`.

## 5. Pega applications

Use the `pega` fixture (`PegaPage`) for UI actions and `sessionApiRequest` (see `api-automation`) for REST calls as the same operator. All Pega tuning (frame selectors, spinner selectors, ignored requests, quiet window) lives in `pega/config/pega.config.ts`, never in tests.

- **Targets, in order:** `{ role, name }`, `{ label }`, `{ testId }` (attribute `data-test-id`), `{ property: 'Customer.Name' }`, `{ text }`. `css` targets containing `pega-*`, `PegaGadget<N>Ifr`, numeric or hashed ids are rejected. While exploring, note label text, role, `data-test-id` and the property reference rendered in the `name` attribute.
- **How it works:** (1) each action waits for idle (no tracked XHR/fetch/document request pending and no busy indicator visible for the quiet window); (2) it resolves the innermost visible harness/modal iframe (modal first, then `PegaGadget*`, up to three levels, falling back to the page since Constellation has no iframes); (3) it acts, retries up to three times on detached-frame errors, and waits for idle again.

| Need | Do |
|---|---|
| Field with a generated id | `pega.fill({ label: 'First name' }, value)` or `{ property: 'FirstName' }` |
| Dropdown | `pega.select({ label: 'Country' }, 'Norway')` |
| Grid data | `pega.readTable({ role: 'table' })` |
| Assertion on the active frame | `expect(await pega.locate({ label: 'Status' })).toHaveText('Open')` |
| Custom wait | `await pega.waitForIdle()` |
| Spinner not detected | add its selector to `busySelectors` |
| Wrong frame chosen | adjust `pegaFrameOptions.selectors` |
| Pega page object | extend nothing: compose `PegaPage` calls in a page object under `pages/` or call them in the test |
| Login | `tests/pega/pega.setup.ts`, stored in `.auth/pega/operatorStorageState.json` |
| Tool run | `pegaTools.run('fillForm', { fields: [{ target: { property: 'FirstName' }, value: 'Ada' }] })` |

Verify with `npm run test:framework` (mock Pega pages, no server needed), then `npm run test:pega` against a real environment.

## Troubleshooting

- **Strict-mode violation:** locator too loose. Add `{ exact: true }`, scope to a parent, or use a more specific role.
- **Element not attached:** the action raced a navigation or frame swap. Add `waitForResponse` or a web-first assertion in the action method.
- **Pega fields not committing or detached frames:** use `pega.fill` (it tabs out and retries) and check `busySelectors` and frame selectors in `pega.config.ts`.
- **Anything else failing:** see the debugging section of `framework`.

```
